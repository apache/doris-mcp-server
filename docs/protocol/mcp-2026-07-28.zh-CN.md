# MCP 2026-07-28 合同

[English](mcp-2026-07-28.md) | 简体中文

Apache Doris MCP Server 在 Streamable HTTP 和 stdio 上共用一套 MCP SDK v2
协议核心。MCP Wire Revision、Doris MCP Server 包版本和 Python SDK 版本是三个
独立标识。

权威协议参考：

- [MCP 2026-07-28 规范](https://modelcontextprotocol.io/specification/2026-07-28)
- [MCP 2026-07-28 变更](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- [Streamable HTTP 传输](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

## 兼容矩阵

| Client 协议 | Streamable HTTP | stdio | 合同 |
|---|---|---|---|
| `2026-07-28` | `/mcp` 首选 | 首选 | 无状态、自包含请求，经过完整 Release Gate |
| `2025-11-25` | `/mcp/legacy` 显式开启 | 仅迁移 | 接受旧初始化，但不创建 HTTP Session |
| `2025-06-18` 及更早 | 不保证 | 不保证 | 应升级 Client |
| HTTP+SSE `2024-11-05` | 不支持 | 不适用 | 独立 SSE 端点已移除 |

`ENABLE_LEGACY_HTTP_ADAPTER=true` 只启用隔离的旧 HTTP 路径，不会改变
`/mcp`、恢复 1.0 以前 Tool 名称或创建 Session。

## 现代请求元数据

每个 `2026-07-28` 请求都在 `params._meta` 中携带：

- `io.modelcontextprotocol/protocolVersion`：`2026-07-28`
- `io.modelcontextprotocol/clientCapabilities`：本次请求能力或 `{}`
- `io.modelcontextprotocol/clientInfo`：Client 名称和版本（推荐）

`server/discover` 是可选方法，用于报告协议版本、能力和确定性产品身份；正常请求
仍然自包含。

## Streamable HTTP 合同

每个 `POST /mcp` 发送一个 JSON-RPC 请求：

| Header | 必需 | 规则 |
|---|---|---|
| `Content-Type` | 是 | `application/json` |
| `Accept` | 是 | 同时包含 `application/json` 与 `text/event-stream` |
| `MCP-Protocol-Version` | 是 | 与 `_meta` 中版本一致 |
| `Mcp-Method` | 是 | 与 JSON-RPC `method` 精确一致 |
| `Mcp-Name` | 命名调用 | 与 `params.name` 或 `params.uri` 一致 |

Header 名称大小写不敏感，Method 与 Name 值大小写敏感。必需 Header 缺失或与
Body 不一致时返回 HTTP 400 与协议 `HeaderMismatch`（`-32020`）；不支持的协议
返回 `UnsupportedProtocolVersion`（`-32022`）。

示例：

```bash
curl --request POST http://127.0.0.1:3000/mcp \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json, text/event-stream' \
  --header 'MCP-Protocol-Version: 2026-07-28' \
  --header 'Mcp-Method: server/discover' \
  --data '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "server/discover",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {
          "name": "example-client",
          "version": "1.0.0"
        }
      }
    }
  }'
```

如果 Name/URI 不能安全放入纯 ASCII Header，应使用传输规范定义的 Base64 Header
编码。

## stdio 合同

stdio 使用相同 JSON-RPC Body 与 `_meta`，但没有 HTTP Header。Host 启动 Server
子进程，通过 stdin/stdout 交换 Frame。任何普通日志都不能写入 stdout。

现代 stdio 请求合同同样无状态；旧 stdio 初始化只能作为有界迁移路径。

## List 分页

`resources/list`、`tools/list`、`prompts/list` 每次最多返回
`MCP_LIST_PAGE_SIZE` 个稳定有序条目。存在 `nextCursor` 时，下一次请求应原样传入
`cursor`。

Cursor 是 HMAC 认证的显式状态句柄，绑定：

- List 类型、Scope 和 Resource；
- 可见列表快照；
- Authorization Context/Principal；
- 过期时间。

它不依赖协议 Session、传输连接或 Worker 内存。可见性变化、过期、篡改、身份
变化或跨 List 复用都会返回 `Invalid Params`。

同一 CLI 启动的 Worker 默认共享一次启动 Secret。如果独立实例后有负载均衡，
连续分页可能进入不同实例，应配置同一个高强度 `MCP_STATE_HANDLE_SECRET`。
句柄只签名、不加密，不能包含凭据、SQL 或查询数据。详见
[ADR 0002](../decisions/0002-explicit-state-handles.md)。

List 失败不会伪装成成功空列表。权限、后端和内部错误保持类型化失败语义，因此
成功返回空集合才真正表示当前身份没有可见条目。

## Tool Schema

Tool `inputSchema` 与 `outputSchema` 使用 JSON Schema 2020-12。执行前：

1. 编译可见定义并按 Schema 预算检查；
2. 校验调用参数，不回显被拒绝值；
3. 成功 Structured Output 必须在跨越协议边界前再次校验。

Schema 必须自包含，只接受同文档 Fragment Reference；不会获取 HTTP、File 或相对
外部引用。递归引用和超限 Schema/Instance 都会 Fail Closed。

默认硬限制包括 Schema 64 KiB、2,048 节点、深度 32、64 个组合分支和 64 个
Reference。输入/结构化输出 Instance 限制为 1 MiB、10,000 节点、深度 32 和
有界字符串。

## Trace Context

Client 可以在 `params._meta` 中提供 W3C `traceparent`、`tracestate` 和
`baggage`。Server 会：

- 传播前校验大小和形态；
- 独立忽略畸形字段；
- 脱敏凭据型 Baggage 值；
- 把 Context 限定在一个请求内；
- 绝不把 Trace Carrier 复制到面向模型的 Tool/Resource/Prompt 结果。

HTTP 和 stdio 使用同样的 Message-level Carrier；这些字段不是独立 MCP HTTP
Header。

## Subscription 边界

Server 不声明 `subscriptions/listen`。Tool 与 Prompt Catalog 没有运行时变更通道，
而 Doris 元数据尚未向该进程提供可靠的跨 Worker Change-event Source。缓存过期
或轮询不被冒充成事件。

Discovery 因此报告 `listChanged: false`，Resource 报告 `subscribe: false`，
Client 应显式刷新。详见
[ADR 0001](../decisions/0001-subscriptions-require-change-events.md)。

## 协议错误与恢复

- Header/Body 不一致：修复请求，不要原样重试。
- 协议版本不支持：升级，或显式选择旧 Adapter。
- Cursor/状态句柄无效：不带 Cursor 重新开始 List。
- Tool 参数无效：使用当前发现到的 Schema。
- 领域 Manifest 陈旧：重新发现领域。
- 无状态 HTTP 请求中断：使用新 JSON-RPC Request ID 重试。

不要依赖 `Mcp-Session-Id`、Sticky Session、已移除的 HTTP GET Stream、
`Last-Event-ID` 或可恢复 SSE 行为。
